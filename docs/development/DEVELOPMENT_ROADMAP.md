# 多城市经济与政治模拟游戏：后续开发计划

> 状态：持续维护中 ｜ 最后更新：2026-11-02
>
> 本文是我们共同维护的进度与计划，不代替《项目总计划 v0.2》。策划已确定事项、技术建议和待决定事项要分开记录；未实现的功能不能标记为已完成。日期是记录日期，不是开发期限。

## 1. 项目当前状态

- 技术方向：TypeScript + Phaser + Electron；地图表现与人口、经济等模拟规则分离。
- 企业、人口、股票、公司治理、政府政策和交通等机制的可运行原型已集成至 `C:\CODING` 的 `main`，仍是可继续深化的原型。
- 集成前验证了 171 项自动测试、构建和隔离桌面冒烟；桌面冒烟不代表新增政策和交通界面的所有场景均已验证。
- 世界地图采用虚构世界中的一小片平面区域。现有场景使用 Kenney 备用资源及 Kenney UI；Rasak 主资源尚未核验或集成。
- 政治、科技、房地产等仍需继续设计，演示规则不等于完整机制。

## 4. 建议开发顺序

以下是技术建议，具体优先级由用户决定；不是已确认的游戏规则。

**当前方向**：优先讨论和深化企业自动经营与成立倒闭、政府政策与领导人、城市和城际交通，以及这些机制与人口、经济和投资之间的联动。具体尚未确认的公式、数量限制和权限可以作为可替换的原型假设，但不得描述为用户已确定。

1. **巩固现有版本**：保护存档和已有成果，结合实际游玩继续验证机制的联动和数值。
2. **深化经济循环**：讨论人口、就业、收入、消费、企业经营、商品生产与定价、贸易和 GDP 之间的反馈，明确哪些规则已有定论、哪些仍需设计。
3. **深化企业与投资**：讨论企业目标和经营风格、创办与退出、融资、股票权利、董事会与居民投资实体如何联动。
4. **深化政府与城市**：讨论领导人、政策、税收、财政预算和交通网络如何影响居民、企业与跨城贸易；玩家市长与 AI 政府的操作权限分别明确。
5. **继续规划其他系统**：依用户选择讨论科技、政治、房地产等；国家、外交和军事等留待基础机制稳定后再讨论。上述顺序是建议，不代表具体玩法规则已确定。
6. **后续完善美术资源**：按需要核验资源及许可，逐步丰富场景表现，不阻塞机制规划。

### 世界地图设计方向（讨论中）

- 用户已明确世界地图采用平面的虚构地图，不使用真实地图；初版先做虚构世界中的一小片区域。目前原型是一张包含三座演示城市的区域战略地图。
- 世界地图的具体地理形态、视觉风格、玩家观察层级和城市分布仍需讨论，不能当成已经确定；用户要求地图问题暂时讨论到此。
- 后续再决定地形、海岸线、河流、城市、道路、区域边界、贸易路线和资源分布如何与经济、运输和政治玩法联动，并核验地图数据及素材的使用条件。

### 企业与跨城市贸易方向（用户提出，细则待设计）

- 每家企业作为一个独立的整体参与经营和对外交易；城市中存在多家企业，不能把它们的经营与交易简单合并为一家企业。
- 企业应具备股票、商品、股权、董事会等组成部分，相关系统相互影响。商品的生产、采购和销售、企业经营、股权和董事会之间的具体规则需要继续设计；不能把股东和董事会成员当作天然相同。
- 用户确定股票分两类：一类有投票权，一类只能分红。企业作为买家，在股票市场买入的股票都有投票权；是否同样适用于个人买入的股票尚未确定。
- 企业融资时可以针对不同出资方分别选择是否给予投票权，例如给某家投资企业投票权、不给另一家；须准确记录每个出资方的权利，不能只用公司级统一开关。具体发行和谈判规则、权利的转让及持续性、有投票权股票是否分红、每票权重与董事会规则待设计，不能预设既有股东权利可被任意更改。
- 用户确定普通人口也会参与股票购买：每个城市的居民按群体划分为多个居民投资实体，作为投资主体参与股票系统；不为每个普通居民建立独立投资者。主分支已有相关原型；具体群体划分、个人股票购买的权利、交易与定价、分红归属及投票方式仍待进一步讨论。
- 用户明确：居民投资实体的内部情况不需要在玩家 UI 中展示；人口信息使用美观的动态饼状图，鼠标悬停在各部分有浮动效果。具体展示哪些人口分类、动画方式和悬停信息待设计；不同统计口径不能错误相加为总人口。
- 跨城市交易既可以由企业之间进行，也可以由政府牵头形成贸易协议，让本市多家企业与其他城市多家企业参与商品购买和出售。
- 用户已明确：政府牵头的贸易协议中，企业可以拒绝参加。仍需明确协议参与方和签署方式、各方买卖商品与数量价格、期限、协议生效条件、履约和退出、违约以及政府权限；不能默认政府可强迫企业参加或将企业库存与资金合并。
- 主分支已有企业库存、生产、交易、股权、治理及政府牵头协议的原型，完整玩法和细则仍需进一步设计。

### 事件通知系统（用户提出，细则待设计）

- 在游戏最上方 UI 的正下方紧挨着设置事件通知区域。
- 通知玩家个人相关事件；根据玩家是否拥有企业，通知其相关企业事件；根据玩家是否担任市长，通知其相关城市事件。具体触发条件和通知内容后续细化。
- 用户明确：通知出现时上方只显示小图标；玩家点击后才打开可拖动的小窗口，查看具体通知内容。
- 用户明确：通知及其他游戏 UI 的消息只展示玩家需要看的内容，不展示系统信息等无关内容。玩家需要知道的错误、存档状态或重要经营事件应使用易懂的游戏语言表达，具体显示方式待设计；不要将技术日志作为玩家消息展示。
- 用户明确：玩家只是持有企业少量股票时，只通知分红、与玩家投票权相关的投票和重大变化；日常经营情况由玩家进入企业页面查看，不主动推送。哪些情况构成重大变化仍需讨论。
- 待讨论：具体通知事件清单、拥有企业的判定口径（持股、控股或经营权）、持股较多但未取得控制权时的范围、取得控制权后的通知、市长负责城市的范围、多条通知如何呈现、已读和历史、优先级及跳转操作；不能默认一持股就等于控制企业，也不能向无投票权的持有人发送可参与投票的通知。
- 主分支已有通知原型；具体通知范围和后续细则仍需讨论。
