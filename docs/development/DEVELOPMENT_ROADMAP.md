## 2. 当前问题与近期验收

### P0：保护无法读取的自动存档

- **状态：已在机制开发分支修复并测试，尚未集成主分支；原问题影响存档安全。**
- 已复现：自动存档读取返回“存档过大”等失败时，程序未暂停自动保存；下一次自动保存可能覆盖原文件。缺失字段但能读取的损坏存档已有保护，不能将两种情况混为一谈。
- 期望：区分首次运行的“文件不存在”和“文件存在但读取失败”；后者提示具体问题、暂停自动覆盖、保留原文件与当前游戏状态。明确恢复方式，不能因普通读取失败静默覆盖。
- 验收：覆盖过大、读取错误、文件不存在、损坏内容以及正常存读档；核对原文件字节保持不变，并完成桌面场景验证。
- 位置：`C:\CODING-worktrees\first-playable\src\app\gameStore.ts`，并检查平台存档接口的错误分类。

### P1：明确采购与借款的关系

- **状态：已复现，规则待决定。** 当企业有采购缺口但市场无供应时，采购没有成交，仍可能预先借入营运资金，现金和债务同步增加。复验示例中企业新增现金与债务各 186,300,000，采购额为零。
- 待决定：借款是企业独立的备资行为，还是只在交易成功时与采购一同发生？前者需明确借款用途、触发条件及展示；后者需将相关借款纳入交易提交和失败回滚。
- 验收：对无供应、资金不足、部分成交和成功采购分别验证资金、债务、库存和记录。不能将固定的跨城合同交易回滚误认为覆盖了所有采购情形。
- 位置：`C:\CODING-worktrees\first-playable\src\simulation\production\production.ts`。

### P1：机制盘点新发现的基础问题

## 4. 建议开发顺序

以下是技术建议，具体优先级由用户决定；不是已确认的游戏规则。

**最新授权（2026-11-01）**：用户要求将 [游戏内容讨论与设计记录](../design/GAME_DESIGN_DISCUSSIONS.md) 中目前已确认的企业自动经营及成立倒闭、政府政策与领导人、城市交通和城际交通一并交给外部 AI 开发，并修复桌面验证脚本的存档版本硬编码。15 项已确认政策均需纳入交付范围。具体尚未确认的公式、数量限制和权限可采用可替换、明确记录的原型假设，不得描述为用户已确定。任务基于机制分支 `b50d6b5`，独立 worktree 开发，验收后再决定集成。

1. **保护现有进度**：解决自动存档读取失败可能覆盖原文件的问题；决定采购备资规则并按决定验证。
2. **完成资源与视角验证**：核验 Rasak 资源和许可，比较视角方案，拼出一块可操作的样板街区。
3. **完成初版验收与集成**：复查桌面运行、关键模拟约束、保存读取及资源清单；架构负责人审查外部 Agent 提交，再按 Git 工作流决定合并 `develop` 和 `main`。
4. **完善可玩的经济循环**：审查人口、工资、消费、企业库存、生产、价格、贸易和 GDP 的数值及反馈；梳理演示性的区域外出口、营运信贷和债务重组，决定保留或替换。补充足以解释结果的界面和事件记录。
5. **发展玩家与城市系统**：依用户选定顺序设计投资交易、企业控制、科技、政治和房地产；现有占位展示不计为完整功能。优先明确玩法规则和数据权威，再拆分外部 Agent 任务。
6. **长期扩展**：在基础系统稳定后，再讨论国家、外交、军事、更多社会系统及性能扩展。

### 企业与跨城市贸易方向（用户提出，细则待设计）

- 每家企业作为一个独立的整体参与经营和对外交易；城市中存在多家企业，不能把它们的经营与交易简单合并为一家企业。
- 企业应具备股票、商品、股权、董事会等组成部分，相关系统相互影响。商品的生产、采购和销售、企业经营、股权和董事会之间的具体规则需要继续设计；不能把股东和董事会成员当作天然相同。
- 用户确定股票分两类：一类有投票权，一类只能分红。企业作为买家，在股票市场买入的股票都有投票权；是否同样适用于个人买入的股票尚未确定。
- 企业融资时可以针对不同出资方分别选择是否给予投票权，例如给某家投资企业投票权、不给另一家；须准确记录每个出资方的权利，不能只用公司级统一开关。具体发行和谈判规则、权利的转让及持续性、有投票权股票是否分红、每票权重与董事会规则待设计，不能预设既有股东权利可被任意更改。
- 用户确定普通人口也会参与股票购买：每个城市的居民按群体划分为多个居民投资实体，作为投资主体参与股票系统；不为每个普通居民建立独立投资者。居民投资实体需与收入、消费、储蓄、持股和分红等机制衔接。具体群体划分、个人股票购买的权利、交易与定价、分红归属及投票方式均待进一步讨论；现有原型尚无居民股票购买机制。
- 用户明确：居民投资实体的内部情况不需要在玩家 UI 中展示；人口信息使用美观的动态饼状图，鼠标悬停在各部分有浮动效果。具体展示哪些人口分类、动画方式和悬停信息待设计；不同统计口径不能错误相加为总人口。
- 跨城市交易既可以由企业之间进行，也可以由政府牵头形成贸易协议，让本市多家企业与其他城市多家企业参与商品购买和出售。
- 用户已明确：政府牵头的贸易协议中，企业可以拒绝参加。仍需明确协议参与方和签署方式、各方买卖商品与数量价格、期限、协议生效条件、履约和退出、违约以及政府权限；不能默认政府可强迫企业参加或将企业库存与资金合并。
- 初版已有企业库存、生产、交易、玩家持股和分红的简化演示；完整股票交易、董事会、企业控制权及政府牵头的多企业协议尚未实现，不能视为已完成。

### 事件通知系统（用户提出，细则待设计）

- 在游戏最上方 UI 的正下方紧挨着设置事件通知区域。
- 通知玩家个人相关事件；根据玩家是否拥有企业，通知其相关企业事件；根据玩家是否担任市长，通知其相关城市事件。具体触发条件和通知内容后续细化。
- 用户明确：通知出现时上方只显示小图标；玩家点击后才打开可拖动的小窗口，查看具体通知内容。
- 用户明确：通知及其他游戏 UI 的消息只展示玩家需要看的内容，不展示系统信息等无关内容。玩家需要知道的错误、存档状态或重要经营事件应使用易懂的游戏语言表达，具体显示方式待设计；不要将技术日志作为玩家消息展示。
- 用户明确：玩家只是持有企业少量股票时，只通知分红、与玩家投票权相关的投票和重大变化；日常经营情况由玩家进入企业页面查看，不主动推送。哪些情况构成重大变化仍需讨论。
- 待讨论：具体通知事件清单、拥有企业的判定口径（持股、控股或经营权）、持股较多但未取得控制权时的范围、取得控制权后的通知、市长负责城市的范围、多条通知如何呈现、已读和历史、优先级及跳转操作；不能默认一持股就等于控制企业，也不能向无投票权的持有人发送可参与投票的通知。
- 当前原型已有事件日志与提示，尚未确认达到上述按身份筛选、固定位置的完整通知系统要求，不应标记为已实现。
